\section{Shell Scripts and State}

\begin{frame}{State}
  \begin{itemize}
    \item The shell is your main interface with the operating system. You can
      run other programs, manage the filesystem, etc.
    \item Usually you interface via the CLI, but you can automate this with
      scripts.
    \item Side effects are the \textbf{entire point} of many shell scripts (e.g.
      setup scripts).
      \begin{block}{External State}
        \begin{itemize}
          \item Working Directory (!!!! if you use relative paths)
          \item Filesystem contents
          \item Environment variables passed by the system
        \end{itemize}
      \end{block}
    \item Do not assume shell scripts are like 6.101 assignments.
    \item You are responsible for writing your own reset button (reverting any
      changes the shell script made if necessary).
  \end{itemize}
\end{frame}

\section{Understanding the File System}

\begin{frame}{Locating Yourself in the File System}
  \begin{itemize}
    \item You \textbf{must} internalize this for the class to make sense.
    \item There are relative paths and absolute paths (know which one you use).
    \item You must reason correctly about paths or else you will get \texttt{no
      such file} errors everywhere.
    \item ASK: where is the file I need, and where is it relative to where I am?
  \end{itemize}
  \begin{block}{Relative Path Examples}
    \begin{itemize}
      \item \texttt{../myfile.sh}
      \item \texttt{./myfile.sh}
      \item \texttt{myfile.sh}
      \item \texttt{some/dir/../myfile.sh}
    \end{itemize}
  \end{block}
  \begin{block}{Absolute Path Examples}
    \begin{itemize}
      \item \texttt{/workspace/myfile.sh}
      \item \texttt{/home/myuser/myfile.sh}
    \end{itemize}
  \end{block}
\end{frame}

\begin{frame}[fragile]{Working Directory}
  \begin{itemize}
    \item Relative paths are relative \textbf{to what}??
    \item \texttt{pwd} gets the current working dir, \texttt{cd} changes the
      working directory.
    \item Most of the programs and arguments you invoke will be working
      directory dependent. (relative paths)
    \item If you have a  script that is attached to a certain repository, you
      need to work to prevent this.
  \end{itemize}
  Why is this so emphasized?
  \begin{itemize}
    \item It helps lock down assumptions about the state of the other system.
      They didn't mess with your repo means your script works.
    \item A lot of your scripts will be tightly coupled with other parts of your
      source code (e.g. copying over config files or running other scripts in
      the same repo).
    \item Naive \texttt{cp ./myconfig \$DIST/config} might not work
  \end{itemize}
  Live Demo with paths!
\end{frame}

\begin{frame}[fragile]{Working Directory Demo}
  Let's say you have the following project structure:

\begin{frame}[fragile]{Working Directory Demo}
  Bad \texttt{setup.sh} (explodes if you run it from \texttt{/}):
\begin{lstlisting}[language=bash]
#!/usr/bin/env bash
# what is this relative to???
pip install -r ./requirements.txt
python3 ./devserver.py
\end{lstlisting}
Better \texttt{setup.sh}:
\begin{lstlisting}[language=bash]
#!/usr/bin/env bash
DIR="$(realpath "$(dirname "$0" )" )"
cd "$DIR"
# now we can run this knowing all relative paths are relative to repository root.
pip install -e ./requirements.txt
python3 ./devserver.py
\end{lstlisting}
What is dirname and realpath (symlink resolution)?
\end{frame}

\begin{frame}{File System Permissions}
  Regular Linux files have three main permissions attached to them:
  \begin{enumerate}
    \item Reading (\texttt{cat myfile} does this)
    \item Writing (If you edit a file with a text editor)
    \item Executing (When you run a script)
  \end{enumerate}
  The kernel can grant or deny any of these permissions to you.
  \texttt{chmod} modifies these permissions.
\end{frame}

\section{Running Processes}

\begin{frame}[fragile]{Commands as Programs}
\begin{itemize}
  \item Some set of shell built-ins
  \item But most commands are \textbf{names for executable files on your system}
  \item They are just shortened for convenience (we'll get to this)
\begin{lstlisting}[language=bash]
# this is a valid shell script (albeit very brittle).
/bin/mkdir myfolder
/usr/bin/gcc file.c -o file
\end{lstlisting}
  \item Successful programs exit with an exit code of 0, non-zero means some
    error.
\end{itemize}
\end{frame}

\begin{frame}[fragile]{Exit Codes}
  \begin{itemize}
    \item Some runtimes use sophisticated exceptions, result types
    \item Errors in UNIX-like operating systems are handled via exit codes.
    \item Successful programs exit with 0, non-zero means some error.
    \item Most shell interpreters will store the exit status of the last exit
      code in \texttt{\$?}.
  \end{itemize}
\begin{lstlisting}[language=bash]
mkdir -p /tmp/hello
# prints 0
echo "$?"
# prints 1 (because it already exists)
mkdir /tmp/hello
echo "$?"
\end{lstlisting}
\end{frame}

\begin{frame}[fragile]{Pipes and Redirection}
  \begin{itemize}
    \item The I/O streams to know are stdin (0), stdout(1), stderr(2)
    \item They are actually called file descriptors (see 6.1810), but just think
      of them as streams that can be redirected.
    \item The redirection gets read left to right.
    \item You can redirect or pipe program stdout into the stdin of another
      program (pipes).
\begin{lstlisting}[language=bash]
# count the number of files and output that
ls | wc -l
# redirects standard output into a file (truncate file)
ls | wc -l > count.txt
# Same as above, except don't truncate
ls | wc -l >> count.txt
# this will show two lines.
cat count.txt
\end{lstlisting}
How might we use truncate vs append behavior when constructing a log?
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{Stdout vs Stderr Demo}
\begin{lstlisting}[language=c]
// hello.c
#include <unistd.h>
int main() {
  char out[] = "stdout\n";
  char err[] = "stderr\n";
  // write to standard output
  write(1, out, sizeof(out));
  // write to standard error
  write(2, err, sizeof(err));
}
\end{lstlisting}
\begin{lstlisting}[language=bash]
gcc hello.c -o hello
# this will output "hello" twice
./hello
# this will output one "hello" and one 1
./hello | wc -l
# this will output 2 because we merge stderr into stdout
./hello 2>&1 | wc -l
\end{lstlisting}
(Blackboard for how the streams get modified)
\end{frame}

\begin{frame}[fragile]{Environment Variables}
Shell Variables are:
\begin{itemize}
  \item Confined to the process
  \item Set by the syntax \texttt{VAR=value}
  \item Referenced with dollar sign syntax \texttt{VAR="\$ANOTHERVAR"}
\end{itemize}
Environment Variables are:
\begin{itemize}
  \item External variables that can influence processes
  \item Passed from parent to child.
  \item You can access them as variables when writing shell scripts.
  \item Ordinary shell variables will not become environment variables unless
    you use the \texttt{export} keyword.
  \item You will often manipulate \texttt{PATH}, \texttt{CC}, \texttt{LDFLAGS},
    and a bunch of other environment variables to get the build results you
    want.
  \item In python, you extract process env vars via \texttt{os.environ}
\end{itemize}
\end{frame}

\begin{frame}[fragile]{Environment Variable Demo}
tester.sh

# regular bash variable (will not get exported)

\end{frame}

\begin{frame}[fragile]{So what is PATH?}
  \begin{itemize}
    \item The bane of intro CS students trying to set up their environments
    \item Basically tells you which executables you can shorthand (instead of
      writing out a full path).
    \item Use \texttt{command -v} to figure out which executable is being
      called.
    \item A colon-separated series of paths which the shell will lookup.
    \item Homebrew, Virtual Envs, Conda, \dots change the world by messing with
      this variable (\texttt{python3} points to a different interpreter)!
  \end{itemize}
Live Demo!
\begin{lstlisting}[language=bash]
export PATH="/usr/bin:/bin"
# bash will search /usr/bin/myprogram, followed by /bin/myprogram.
myprogram
# you can see whether it is /usr/bin/myprogram
command -v myprogram
export PATH="/my/installation:/usr/bin:/bin"
# now bash will search /my/installation first.
command -v myprogram
\end{lstlisting}
\end{frame}

\begin{frame}[fragile]{Control Flow}
  \begin{itemize}
    \item if, for, and while all exist, and are driven by exit codes
    \item conditionals are determined by exit code (0 is true, non zero is false!)
    \item You probably want to use \texttt{\&\&} and \texttt{||} more
    \item Functions have no scope! They just help section code
    \item \texttt{test} can be used to check for file existence.
  \end{itemize}
\begin{lstlisting}[language=bash]
if ! test -f myfile.txt; then
  echo 'hello' > myfile.txt
fi
# below does the same thing as above
! test -f myfile.txt && echo 'hello' > myfile.txt
# so does below
test -f myfile.txt || echo 'hello' > myfile.txt
\end{lstlisting}
\end{frame}

\section{Defensive Scripting}

\begin{frame}{A Tale of Two Scripts: Part 2}
So what's wrong with the below? What are the possible failure modes?
\lstinputlisting[language=bash]{badscript.sh}

\only<2->{
\begin{itemize}
  \item<2-> dependent on the script invoker's working directory!
  \item<3-> mkdir or grep not found (The user screwed up \texttt{\$PATH})
  \item<4->errors propagate (no ``exceptions'' unless forced)
  \item<4->Bonus: \texttt{/bin/bash} is not standard! Only \texttt{/bin/sh} is.
    There are systems that don't have \texttt{/bin/bash}
\end{itemize}
}
\end{frame}

\begin{frame}[fragile]{A More Defensive Script}
\begin{lstlisting}[language=bash]
#!/usr/bin/env bash
# exit if any part encounters a bad exit code or undefined env var
set -euo pipefail
# parent directory of our script
DIR="$(realpath "$(dirname "$0" )" )"
# -p for idempotency, our working directory is now deterministic.
mkdir -p "$DIR/out" && cd "$DIR/out"
# test for existence first.
test -r text.txt && grep foo text.txt > result
\end{lstlisting}

\begin{block}{Design Decisions}
\begin{itemize}
  \item Do we want silent failure or be loud?
  \item Do we destroy history of result? (\texttt{>} versus \texttt{>>})
  \item We just need to be deliberate with what behavior we allow
\end{itemize}
\end{block}
\end{frame}

\begin{frame}{Some General Principles}
  \begin{itemize}
    \item Even if a script works, you need to be skeptical.
    \item If your entire working environment and build artifacts were destroyed
      and then reconstructed, your script must still work or error cleanly.
  \end{itemize}
\end{frame}

\section{Host vs Target Systems}

\begin{frame}[fragile]{Host vs Target}
  \begin{itemize}
    \item Will be a huge part of lab pain
    \item You are on a \textbf{Host System}, building artifacts that will go in
      a separate \textbf{Target System} (Blackboard time)
    \item The target system must be wholly self-sufficient. No dependence on:
      \begin{itemize}
        \item Host libraries (This one's subtle), \textbf{especially the libc}
        \item Host services
        \item Host configuration files
      \end{itemize}
    \item You need to carefully manipulate environment variables and options
      because cross-compiling is not assumed!
\begin{lstlisting}[language=bash]
# working dir is the root of some source tree
export CC="/path/to/custom/cc"
export CFLAGS="-nostdinc -I/custom/include/prefix -static"
export LDFLAGS="-L/custom/lib/prefix -static"
./configure --prefix="/usr"
make
make install DESTDIR="/path/to/your/rootfs"
\end{lstlisting}
  \end{itemize}
\end{frame}

\begin{frame}{Core concepts Regarding Docker}
  \begin{itemize}

    \item An image is the template for a container (debian)
    \item You build images and then run containers based off that image.
    \item You can also execute commands inside a running container like an
